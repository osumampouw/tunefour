Infrastructure, Docker & GCP

How Tunefour runs — locally today, and on Google Cloud later. Target cloud is GCP. Written for someone who understands the concepts but hasn't used Docker or Terraform hands-on yet.

Deploy target: Google Cloud Platform

Docker & Docker Compose local dev

A container is a lightweight, isolated unit that packages a program with everything it needs to run, so it behaves identically on any machine. Docker Compose runs several containers together from one file — perfect for spinning up the services our app depends on without installing each by hand.

docker-compose.yml, explained

It defines three services:

ServiceImagePort(s)Role
postgrespostgres:16-alpine5432The relational database — source of truth.
redisredis:7-alpine6379Cache + WebSocket pub/sub fan-out.
miniominio/minio9000 / 9001S3-compatible object storage — stands in for GCP Cloud Storage locally.

Key pieces of each service definition:

  • Ports ("5432:5432") map the container's port to your laptop, so the app connects at localhost:5432.
  • Volumes (pgdata, miniodata) persist data on disk so it survives docker compose down / restarts.
  • Healthchecks let Docker report when a service is actually ready (not just started).
  • Environment sets the dev credentials (user/password/db).

The commands you'll use:

docker compose up -d      # start all three in the background
docker compose ps         # see what's running + health
docker compose logs -f    # follow logs
docker compose down       # stop them (data kept in volumes)
Why MinIO? You can't run Google Cloud Storage on your laptop, but MinIO speaks the same S3 API, so the server's storage code works identically in dev and against GCP later. This is the standard "local stand-in" trick.

.env.example configuration

Configuration and secrets don't belong in code. .env.example is a template listing every setting the app reads (database URL, Redis URL, storage keys, JWT secrets). You copy it to .env (which is git-ignored) and fill in real values.

cp .env.example .env     # then edit .env for your machine

The default values already match docker-compose.yml (same ports, same dev credentials), so with the containers up, the app connects out of the box. In production these come from GCP Secret Manager, not a file.

Terraform cloud provisioning · later

Terraform lets you declare your cloud infrastructure in text files and create/update it with a command — "Infrastructure as Code." Instead of clicking around the GCP console, you write what you want and Terraform makes it so, reproducibly and reviewably in Git.

# example: a Cloud Storage bucket for media, declared in a .tf file
resource "google_storage_bucket" "media" {
  name     = "tunefour-media"
  location = "ASIA-SOUTHEAST2"   # e.g. Jakarta region
}
terraform plan     # preview what would change
terraform apply    # create/update the real resources

This lives in infra/ and is post-MVP — safe to learn last. There's no Terraform code yet; the folder is a placeholder.

Local → GCP mapping

Every local piece has a managed GCP equivalent. The app code stays the same; only connection details change (injected via config/secrets).

Local (dev)GCP (production)What it is

Redis containerMemorystore for RedisManaged cache / pub-sub
MinIOCloud StorageObject storage for media (S3-compatible API)
—Cloud CDNServes media fast worldwide via signed URLs
local node processesCloud Run (or GKE)Runs the NestJS server as a container
—Artifact RegistryStores the built container images
—Cloud BuildBuilds images + runs deploy pipelines in the cloud

Recommended shape for Tunefour on GCP Cloud Run for the server + admin (simplest, scales to zero, container-native) → Cloud SQL (Postgres) → Memorystore (Redis) → Cloud Storage + Cloud CDN (media) → Secret Manager (secrets) → Artifact Registry + Cloud Build (build/deploy). Reach for GKE (Kubernetes) only if you outgrow Cloud Run.

Do you need to install Docker & Terraform on your laptop?

Docker — recommended, but you have options

For local dev services You need a container runtime to run docker compose up. On macOS, pick one:
  • Docker Desktop — the standard, easiest (includes the docker CLI + Compose).
  • OrbStack — a lighter, faster macOS alternative, Docker-compatible.
  • colima — free/CLI-only (brew install colima docker docker-compose).
You could even skip Docker for now You already have Postgres 16 and Redis installed via Homebrew (we upgraded them earlier). So you could run those natively (brew services start postgresql@16 redis) and only add minio when you need object storage. Docker is still recommended — it matches production exactly and is one command — but it isn't strictly required to start building.
For building deploy images You do not necessarily need local Docker: GCP Cloud Build builds container images in the cloud from your source. So a common workflow is Cloud Build for images + local Docker only when you want to run/debug a container by hand.

Terraform — not yet

Defer it Terraform is only needed when we provision GCP infrastructure — post-MVP. When we get there you can either brew install terraform locally, or use GCP Cloud Shell in the browser, which has Terraform and gcloud preinstalled (nothing to install on your laptop at all). No need now.

What you WILL want for GCP work (later)

  • Google Cloud CLI (gcloud) — brew install --cask google-cloud-sdk. Authenticates and talks to your GCP project.
  • Terraform (as above) when provisioning.

ORM & Migration Tool — Decision

Choosing how the NestJS server talks to PostgreSQL for Tunefour. Compares Prisma, Drizzle, TypeORM, and Sequelize against our needs.

Decision: TypeORM (Data Mapper pattern) ✅

What we're deciding, and the vocabulary

Our source of truth is PostgreSQL (a SQL database). The server needs to read and write it from TypeScript. Two related jobs:

  • ORM (Object–Relational Mapper): lets you work with database rows as TypeScript objects instead of hand-writing SQL strings. You call db.device.findMany() and it generates the SQL, runs it, and gives you typed results.
  • Migrations: version-controlled, incremental changes to the database structure (add a table, add a column). Like Git commits for your schema — so every environment (your laptop, CI, production) can be brought to the same shape reproducibly. All four tools handle this (with differing ergonomics).
Coming from raw Node + SQL If you've written pg.query("SELECT * FROM ...") by hand, an ORM removes the stringly-typed SQL and the manual mapping of rows to objects — and gives you autocomplete + compile-time checking on your queries. You can still drop to raw SQL when you need to.

What matters for Tunefour

Weighted by our actual situation: a solo/small team, you are learning the stack, NestJS + Postgres, and a schema that will grow (offices, devices, playlists, schedules, users, audit logs).

Prisma Recommended

You define your data model in a dedicated schema.prisma file (its own small language). Prisma generates a fully typed client and manages migrations from that schema.

// schema.prisma — the single source of truth for your data model
model Device {
  id        String   @id @default(uuid())
  name      String
  office    Office   @relation(fields: [officeId], references: [id])
  officeId  String
  createdAt DateTime @default(now())
}
// Fully typed query — autocomplete on every field, typed result:
const devices = await prisma.device.findMany({ where: { officeId } });

Strengths

  • Best-in-class developer experience & docs — the schema is readable, errors are clear, and the guides are excellent for newcomers.
  • Excellent migrations — prisma migrate dev diffs your schema and writes the SQL migration for you; prisma studio is a free GUI to browse data.
  • Strong type-safety without you writing the types.
  • First-class NestJS recipe in the official Nest docs.

Trade-offs

  • Separate schema language (not plain TS) — one more small syntax to learn, though it's simple and well-documented.
  • Some very advanced/complex SQL is done via its $queryRaw escape hatch rather than the fluent API.

Drizzle Strong alternative

A lightweight, "SQL-first" ORM. You define the schema in plain TypeScript, and its query builder mirrors SQL closely. Types are inferred — no code generation step at runtime.

// schema in plain TypeScript
export const devices = pgTable('devices', {
  id: uuid('id').defaultRandom().primaryKey(),
  name: text('name').notNull(),
  officeId: uuid('office_id').references(() => offices.id),
});

// query builder reads like SQL:
const rows = await db.select().from(devices).where(eq(devices.officeId, officeId));

Strengths

  • Very close to SQL — if you like knowing exactly what query runs, there's little "magic." Great for the hand-tuned schedule query.
  • Lightweight & fast, schema is just TypeScript, excellent inferred types.

Trade-offs

  • Steeper if you don't already know SQL well — it assumes more SQL fluency, which is a bigger ask while you're also learning TS.
  • Younger ecosystem than Prisma/TypeORM (growing fast, but fewer tutorials/answers).

TypeORM The classic

The long-standing Node ORM. Uses decorators on classes to define entities — the same decorator style as NestJS itself, so it feels native to Nest.

@Entity()
export class Device {
  @PrimaryGeneratedColumn('uuid') id: string;
  @Column() name: string;
  @ManyToOne(() => Office) office: Office;
}

Strengths

  • Stylistically matches NestJS (decorators/classes); it's the ORM used in Nest's own database docs.
  • Mature, feature-rich, large community.

Trade-offs

  • Weaker type-safety than Prisma/Drizzle — some queries return loosely-typed results.
  • Migrations & some behaviours have historically been finicky (auto-generation quirks, sharp edges), which is rough while you're learning.
TypeORM docs NestJS + TypeORM

Sequelize Familiar, JS-first

A mature, traditional ORM in the same family as TypeORM — model objects with instance methods, a big feature set, many SQL dialects, and a huge community. If you've used it before, the mental model feels like home. NestJS even has an official @nestjs/sequelize integration.

// model definition (v6 style, with the InferAttributes helpers)
class Device extends Model<InferAttributes<Device>, InferCreationAttributes<Device>> {
  declare id: CreationOptional<string>;
  declare name: string;
  declare officeId: string;
}
Device.init({ /* column definitions */ }, { sequelize });

Strengths

  • Familiarity — if you already know Sequelize, you move fast.
  • Very mature, battle-tested, large community, many dialects.
  • Official NestJS support via @nestjs/sequelize.

Trade-offs

  • Weakest TypeScript story here — born as a JavaScript library; typing models needs verbose InferAttributes / InferCreationAttributes generics, and many query results come back loosely typed. Awkward while you're also learning TypeScript.
  • Migrations are hand-written (sequelize-cli) and decoupled from models — no auto-diff from schema changes, unlike Prisma.
  • v7 is a TypeScript-first rewrite that improves this with native decorators, but has been slow to fully land; v6 is what most teams run today.

Vendor lock-in & portability

A key concern for this project: how hard is it to move away from the ORM later? The reassuring baseline — all four are libraries, not frameworks. The database is standard PostgreSQL on GCP Cloud SQL, so the data and schema are always portable. Switching ORMs is a refactor of the data-access code, never a data migration, and none of these bundle external services.

ORMProprietary grammar?Cost of leaving
DrizzleNo (plain TS, SQL-first)Lowest — queries already read like SQL
TypeORMNo (plain TS classes + decorators)Low–moderate — rewrite entities/queries, no special language
SequelizeNo (plain model classes)Low–moderate
PrismaYes — the schema.prisma DSLModerate — bounded to the data layer; migrations are plain SQL you keep
Why this tipped the decision TypeORM uses plain TypeScript (no proprietary schema language), so there is no DSL to be locked into — a deciding factor given a past bad experience with a framework (Keystone.js) whose custom grammar and bundled services made migrating away expensive.

Chosen pattern: Data Mapper

TypeORM supports two patterns; we use Data Mapper.

PatternHow it worksAnalogy
Active RecordThe entity class carries its own persistence methods (device.save(), Device.find()) — extend BaseEntity.Rails; Django-style
Data Mapper ✅Entities are plain data classes; a separate Repository handles persistence (repo.save(device), repo.find()).Hibernate / JPA / Spring Data

We choose Data Mapper because it fits this project's priorities:

  • Testability (TDD): services depend on a repository that can be mocked in unit tests — no database needed to test business logic.
  • Separation of concerns: entities hold shape, services hold logic, repositories hold data access — clean, readable layers.
  • NestJS-native: Nest injects repositories with @InjectRepository(Entity).

Decision

TypeORM (Data Mapper pattern) ✅

TypeORM is the best fit for this project's combination of priorities: mature and battle-tested (the de facto ORM in the NestJS ecosystem), no proprietary DSL (plain TypeScript — avoids the lock-in concern), a traditional-ORM model familiar from Sequelize, first-class NestJS integration, and solid type-safety (a big step up from Sequelize).

Known trade-offs we accept: type-safety is good but not as airtight as Prisma/Drizzle on complex queries, and migration auto-generation can need hand-editing. Both are manageable and neither affects reliability; we use the raw-SQL escape hatch for any query the abstraction handles awkwardly.

Decision status Decided: TypeORM, Data Mapper pattern. Phase 1 begins with the entities for the core domain (offices, devices, playlists, schedules, users, audit log) + the first migration.

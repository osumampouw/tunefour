Phase 1 — Authentication & Access Control (Design)

How admin-portal users sign in and what each role is allowed to do. Authentication is delegated to Google (Single Sign-On via OpenID Connect) — no passwords of our own. Covers the pluggable auth boundary (Google now, Keycloak later — both OpenID Connect), account provisioning, sessions, and role-based access control (RBAC) with office scoping. Read before the code lands in packages/auth and apps/server/src/auth.

Scope of this slice

This slice builds the access-control foundation that every admin API endpoint will sit behind:

  • A pluggable authentication provider — Google SSO (OpenID Connect) now, with Keycloak addable later without touching the rest of the app (Keycloak is also OpenID Connect, so it is the same kind of provider).
  • Account provisioning: a domain whitelist plus an explicit allowlist (only people with a User row may sign in) — we delegate who you are to Google but keep control of who gets in.
  • Session tokens (our own JWT access + refresh) issued after Google verifies identity.
  • Role-based access control: the five roles, and the single-vs-all office scoping model.
  • The /auth endpoints (start sign-in, callback, refresh, me, logout) and a way to bootstrap the first admin.

Not in this slice: the per-endpoint permissions for each entity's CRUD — those are applied in the CRUD slice, which decorates its endpoints with the roles defined here.

Settled earlier Office scoping is single office or all offices (no multi-office) — a deliberate YAGNI choice. A user is scoped to one office (User.officeId set) or is org-wide (officeId null). Multi-office would become a User↔Office join table if a real need appears.
Changed from the previous draft This design replaces the earlier Local (email + password) provider with Google SSO. Consequences: no password storage, so Argon2 hashing and the passwordHash column are dropped; login becomes a redirect to Google rather than a form; the first admin is bootstrapped by email, not by a seeded password.

Terms (plain English)

TermMeaning
AuthenticationProving who you are (signing in). We delegate this to Google.
AuthorizationDeciding what you're allowed to do once signed in. We own this (roles + office scope).
SSO (Single Sign-On)Signing in to our app using an identity you already have elsewhere (your Google account) instead of a new password.
OAuth 2.0The industry-standard protocol for letting one site delegate sign-in to another. It's the "redirect to Google, come back with a code" dance.
OIDC (OpenID Connect)A thin identity layer on top of OAuth 2.0 that returns a verifiable ID token describing who signed in. Google speaks it; so does Keycloak — which is why both fit the same provider.
ID tokenA signed JWT from Google stating who the user is. We verify its signature against Google's public keys, so we can trust its contents without asking Google again.
ClaimsThe fields inside the ID token: email, email_verified, sub (a stable per-user id), hd (the Google Workspace hosted domain), etc.
Redirect URI / callbackThe URL on our server that Google sends the browser back to after sign-in, carrying a one-time authorization code.
state & nonceRandom one-time values we generate per sign-in to defend against cross-site request forgery (CSRF) and token replay. We check they come back unchanged.
PKCE (Proof Key for Code Exchange)An extra OAuth safeguard: we send a hash on the way out and the matching secret on the way back, so a stolen authorization code is useless to an attacker.
JWT (JSON Web Token)A signed token. Google issues one to prove identity; we issue our own as the session token the admin portal sends on each request.
RBAC (role-based access control)Granting permissions by role (e.g. "office-manager") rather than per-user.

Why Google SSO

  • Every employee already has a Google account (Workspace on cermati.com), so there's no new password to create, remember, or reset.
  • Two-factor authentication is Google's job. It's already enforced on the Workspace, so we inherit strong authentication for free and never handle a second factor ourselves.
  • Nothing sensitive to store. No password hashes, no reset flows, no credential-leak surface on our side — the whole class of "we leaked passwords" incidents goes away.
  • Future-proof. Keycloak (a likely future identity provider) is also OpenID Connect, so moving to it later is a configuration change, not a rewrite.

The pluggable authentication boundary

The hard requirement (from CLAUDE.md): a new auth provider must be addable without touching the rest of the app. We get that by drawing a clean line between how you prove who you are (provider-specific) and everything downstream (shared): sessions, guards, RBAC all work on one normalized identity.

The contract

// packages/auth — framework-agnostic (no NestJS, no TypeORM)

/** The normalized identity every provider must produce. */
interface AuthenticatedUser {
  userId: string;
  email: string;
  role: Role;              // from @tunefour/shared-types
  officeId: string | null; // null = all offices (org-wide role)
}

/**
 * A pluggable sign-in mechanism. Redirect-based providers (OpenID Connect)
 * implement a two-step flow: build an authorization URL, then handle the
 * callback the identity provider redirects back to.
 */
interface AuthProvider {
  readonly name: string;   // e.g. 'google-oidc', later 'keycloak-oidc'

  /** Step 1 — where to send the browser to begin sign-in, plus the one-time
   *  values we must remember for step 2 (state, nonce, PKCE verifier). */
  createAuthorizationRequest(): AuthorizationRequest;

  /** Step 2 — exchange the callback's code, verify the ID token, apply our
   *  provisioning policy, and return the normalized identity (or null). */
  completeSignIn(input: CallbackInput): Promise<AuthenticatedUser | null>;
}

Downstream code (token issuing, guards, RBAC) only ever sees AuthenticatedUser. Swapping providers changes only which AuthProvider is wired in.

Why the interface changed shape from the Local draft Local auth was a single authenticate(email, password) call. OpenID Connect is a redirect flow with two steps (send the browser to Google, then handle the code it returns), so the contract now exposes those two steps. Everything after identity is established — the AuthenticatedUser, sessions, guards, RBAC — is unchanged.

Why Google and Keycloak are one provider type

Both are OpenID Connect. The generic OIDC mechanics (discovery, exchanging the code, verifying the ID token) are identical; only the issuer URL and client credentials differ. We'll use a well-maintained OIDC client library (openid-client), which reads each provider's /.well-known/openid-configuration and handles verification. Pointing at Keycloak later means new config, not new code.

Where code lives

packages/auth stays pure (no NestJS, no TypeORM) so it can't accidentally depend on the server's database. The provider needs to look users up, so it depends on a small abstract user store the server implements with TypeORM:

// packages/auth
interface UserAuthStore {
  /** Allowlist lookup: returns the row only if this email is a provisioned user. */
  findByEmail(email: string): Promise<UserAuthRecord | null>; // id, email, role, officeId, isActive
}
Why an abstract store, not the entity directly If packages/auth imported the TypeORM User entity, the shared package would depend on the server app — the wrong direction, and it would break reuse. The UserAuthStore interface keeps the package pure; the server provides a TypeORM-backed implementation. Note it no longer exposes passwordHash — there are no passwords.

NestJS-specific pieces (guards, decorators, controllers) live in apps/server, because they're tied to the framework and shouldn't be in the shared package.

Google SSO provider (MVP)

The GoogleOidcAuthProvider implements the two-step contract above:

  • createAuthorizationRequest() — generates a fresh state, nonce, and PKCE verifier, and builds the Google authorization URL (asking only for the openid email profile scopes — we don't need access to anyone's Gmail or Drive, just their identity). Optionally pins hd to our domain as a hint.
  • completeSignIn() — exchanges the one-time code for tokens, verifies the ID token (signature, issuer, audience, expiry, and that the returned nonce matches), then applies our provisioning policy (next section) to decide whether to admit the user and with what role/office.

Because it's built on generic OIDC, the same class can serve Keycloak later by swapping the issuer and credentials (we may expose it as a configured instance rather than a second class — decided at implementation time).

The sign-in flow

  1. User opens the admin portal and clicks “Sign in with Google.” The browser hits GET /auth/google on our server.
  2. Our server calls createAuthorizationRequest(), stashes the state/nonce/PKCE verifier (short-lived, server-side), and redirects the browser to Google.
  3. Google authenticates the user — password and 2FA happen entirely on Google — and asks for consent the first time.
  4. Google redirects the browser back to GET /auth/google/callback with a one-time authorization code (and the state we sent).
  5. Our server verifies state matches, then completeSignIn() exchanges the code for the ID token and verifies it (signature via Google's public keys, issuer, audience, expiry, nonce).
  6. Provisioning policy runs: the email's domain must be whitelisted and an active User row must exist. If either fails → access denied.
  7. On success we map the row to AuthenticatedUser and issue our own JWT access + refresh tokens. The portal is now signed in and uses those for every API call.
Why we issue our own session token After Google tells us who the user is, the rest of the app shouldn't care that Google was involved. Our own short-lived JWT keeps every request uniform across providers (Google today, Keycloak tomorrow) and means we never call Google again per-request — we only used it to establish identity once, at login.

Provisioning & allowlist

Google will happily authenticate any Google account, so delegating authentication is not the same as granting access. Two gates decide who actually gets in — both must pass:

GateRuleWhy
Domain whitelistThe verified email's domain (and the hd claim) must be in a configured list of allowed domains (e.g. cermati.com). email_verified must be true.Blocks personal Gmail and any outside account outright — defense in depth, independent of the row check.
User allowlistUserAuthStore.findByEmail() must return an active row.Only people an admin has provisioned may sign in; the row also carries their role and office. No row ⇒ no access (we do not auto-create accounts).

So an admin "adds a user" by creating a User row (email + role + office) in the portal — no password, nothing to send them. The person just clicks "Sign in with Google" and they're in, with exactly the role assigned. Removing access = deactivate or delete the row.

Domain whitelist is a list Config holds AUTH_ALLOWED_DOMAINS as a comma-separated list, so additional Workspace domains (acquisitions, brands) can be allowed without code changes. Empty/misconfig ⇒ deny all (fail closed).
Matching by email, with a stable id captured for robustness For MVP we match the allowlist by email (simple, and Workspace emails are stable). On first successful sign-in we also record Google's sub claim into User.externalId — a stable per-account id that survives an email rename. We don't match on it yet (YAGNI), but capturing it now means we can harden later without a data backfill.

Sessions — JWT access + refresh

Unchanged from before: once a provider establishes identity, the app issues its own tokens (uniform across providers):

TokenLifetimePurpose
Access tokenshort (~15 min)Sent on every API request; proves identity. Carries claims: sub (userId), email, role, officeId.
Refresh tokenlonger (~7 days)Used only to get a new access token when it expires, so the user isn't bounced out every 15 minutes.
  • Signed with secrets from the environment (JWT_ACCESS_SECRET, JWT_REFRESH_SECRET — already in .env.example).
  • The access token's claims let guards authorize without a database hit on each request.
  • Lifetimes are configurable, not hard-coded: JWT_ACCESS_TTL (default 15m) and JWT_REFRESH_TTL (default 7d). Values are duration strings (15m, 12h, 7d) parsed by the JWT library's expiresIn.
Session renewal model (MVP) Refresh tokens use absolute expiry: when the refresh token reaches JWT_REFRESH_TTL, the user signs in with Google again — usually a silent redirect, since they still have a live Google session (no password/2FA prompt unless Google re-challenges). Because MVP refresh tokens are stateless (no server-side store), we choose absolute expiry over sliding/rotating: true rotation with stolen-token reuse-detection needs the server-side revocation list, which is deferred (see Out of scope).
Logout & revocation For MVP, logout = the client discards its tokens (POST /auth/logout exists as the portal's hook; it clears the session cookie/token). Server-side refresh-token revocation (a denylist) is deferred (YAGNI) — noted in Out of scope. Short access-token lifetime limits exposure in the meantime.

Roles

The five roles from @tunefour/shared-types, with their intent. (Exact per-endpoint permissions are applied in the CRUD slice; this is the capability overview.) Roles are assigned on the User row — Google tells us who, we decide what they can do.

RoleScopeCan do (intent)
super-adminall officesEverything, including managing users.
content-editorall officesManage content org-wide: assets, playlists, schedules. Not users.
office-managerone officeManage their office's devices and schedules.
front-deskone officeOnly send welcome messages to their own office.
viewerall officesRead-only.
Hard rule from CLAUDE.md front-desk can only send welcome messages, and only to its own office. This is enforced by role (what endpoints) + office scope (which office).

Office scoping

A user's reach is one of two cases, read straight off User.officeId:

officeIdMeaningTypical roles
a valueScoped to that one officeoffice-manager, front-desk
nullAll offices (org-wide)super-admin, content-editor, viewer

So authorization is two independent checks: role decides what kind of action is allowed; office scope decides which office's resources it may touch.

How it's enforced

Two layers, because they answer different questions:

CheckWhereWhy there
Is the request authenticated?Global JwtAuthGuard (opt out with @Public() on the login/callback routes)Uniform; validates our access token and attaches AuthenticatedUser to the request.
Does the role allow this endpoint?RolesGuard (opt in with @Roles(...))Coarse gate — a guard can decide this from the role in the token alone.
Does the resource belong to the user's office?Service layer (a small assertOfficeAccess() helper)Fine-grained — the guard can't know a resource's office without loading it, so the service checks after fetching.
// office-scope helper (service layer)
function assertOfficeAccess(user: AuthenticatedUser, resourceOfficeId: string): void {
  if (user.officeId === null) return;          // org-wide: any office
  if (user.officeId === resourceOfficeId) return; // scoped: only own office
  throw new ForbiddenException();
}

Supporting decorators (all in apps/server): @Public() (skip auth), @Roles(...) (allowed roles), @CurrentUser() (inject the AuthenticatedUser into a handler).

Endpoints (this slice)

Method + pathAuthPurpose
GET /auth/googlepublicBegin sign-in: stash state/nonce/PKCE, redirect the browser to Google.
GET /auth/google/callbackpublic (valid state + code)Google redirects here. Verify, provision-check, issue our JWTs, hand the session back to the portal.

The callback inputs are validated before use; the one-time state is checked against what we stored, and a mismatch is rejected.

How the token reaches the portal Exactly how the callback returns the session to the Next.js portal (an HttpOnly cookie vs. a short-lived redirect hand-off) is a small implementation detail settled when we build the portal login; an HttpOnly cookie for the session is the likely default.

First admin (bootstrap)

Chicken-and-egg: nobody can sign in without a User row, but nobody can create rows without first signing in as an admin. We break it with a config-driven seed — not a hardcoded email list in source:

  • An env var SEED_SUPER_ADMIN_EMAILS holds a comma-separated list (e.g. oby@cermati.com,ops@cermati.com).
  • A one-off command pnpm --filter @tunefour/server seed:admin reads the list and upserts each email as a super-admin row (officeId = null, isActive = true, no password). Idempotent and safe to re-run.
  • Those people then sign in via Google and manage everyone else through the portal. The env list can be emptied once real admins exist.
Why a seed command, not an env check inside login The sign-in path stays pure — it only ever asks "is this email an active User row?" There is no "if email in env then grant super-admin" branch in the hot auth path, so the User table is the single source of truth for who may enter. The env list is just a bootstrap input consumed once.

Data-model impact

Switching to SSO changes the User entity. These are code changes applied at implementation time (gated by approval of this doc); noting them here so the design is complete:

Security notes

  • No passwords at all on our side — the entire password-storage/leak surface is gone. Authentication strength (including 2FA) is Google's responsibility.
  • ID token fully verified: signature against Google's published keys, plus iss, aud, exp, and nonce checks. We never trust token contents we haven't verified.
  • CSRF/replay protection via state + nonce + PKCE on the OAuth flow.
  • Fail closed on provisioning: unknown domain, unverified email, or missing/inactive User row ⇒ denied. We never auto-create accounts.
  • Least privilege at Google: we request only openid email profile — no Gmail, Drive, or other data access.
  • No account enumeration: a denied sign-in returns the same generic error whether the domain, the row, or the active flag was the cause.
  • Secrets from the environment (never committed); separate access/refresh secrets; client secret in Secret Manager in GCP.
  • Short access-token lifetime limits the damage of a leaked session token.

Out of scope (later phases)

  • Keycloak provider — now mostly a configuration change (same OIDC code), not a rewrite. Flip OIDC_ISSUER + credentials when the time comes.
  • Refresh-token revocation list (server-side logout / "log out everywhere").

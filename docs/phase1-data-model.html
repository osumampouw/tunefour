Phase 1 — Data Model (Design)

The database schema for Tunefour: the entities, their columns and relationships, and the decisions behind them. Built with TypeORM (Data Mapper) on PostgreSQL. This doc is meant to be read side-by-side with the entity code in apps/server/src/entities.

Scope of this slice

This covers the data model only — the entities, relations, and the first migration that creates the tables. Authentication, RBAC enforcement, and the CRUD API endpoints are the next Phase 1 slices and get their own design docs. Defining all tables now (including a few fields used by later phases, e.g. device enrollment) keeps the schema coherent and avoids repeated migrations.

Applied principles KISS/YAGNI: columns are limited to what the plan (§3) calls for; no speculative fields. Single source of truth: enums come from @tunefour/shared-types, reused by the entities (no re-listing string values).

Ten entities. The two "polymorphic target" relations (Schedule, WelcomeMessage) are modelled as separate nullable foreign keys plus a targetType enum — see Key decisions for why.

Shared conventions (every entity)

ConventionDetail
Primary keyid: UUID (@PrimaryGeneratedColumn('uuid')). Non-guessable, safe to expose, no cross-table collisions.
TimestampscreatedAt / updatedAt via @CreateDateColumn / @UpdateDateColumn, stored as timestamptz (UTC).
EnumsPostgres enum columns whose values come from @tunefour/shared-types (e.g. enum: Object.values(AssetType)), typed as the shared union.
Flexible datajsonb for open-ended maps (asset metadata, welcome variables, audit metadata).
Money/timeDurations are integer seconds. Wall-clock dayparts are HH:mm strings resolved in the office timezone (see Device/Schedule).
Reading the column tables Column names are colour-coded: a teal name is the primary key (the row's own unique id), and a blue name is a foreign key (it holds the id of a row in another table — the link between tables, e.g. officeId on Device points at the Office it belongs to). Plain (white) names are ordinary data columns.

Key decisions & trade-offs

UUID primary keys

Non-sequential, non-guessable, safe to expose in URLs/APIs, and they let us reference entities across services without collision. Trade-off: slightly larger than integers — a non-issue at this scale (~90 devices).

Polymorphic targets via nullable FKs + a type enum

Schedule and WelcomeMessage can target an office, group, or device. Rather than a generic (targetType, targetId) pair (which loses foreign-key integrity), we use separate nullable foreign keys plus a targetType enum, and enforce "exactly one is set" in the service layer. This keeps real FK constraints and readable joins, at the cost of a few nullable columns. A DB CHECK constraint can be added later to enforce the invariant at the database level.

Enums as Postgres enums, sourced from shared-types

Column values are validated by the database, and the allowed set is defined once in @tunefour/shared-types and reused (enum: Object.values(AssetType)). No duplicated string lists between the shared package and the entities.

No soft-delete (yet)

YAGNI: we don't add deletedAt everywhere now. The AuditLog captures who-did-what history, which covers the immediate need. Soft-delete can be added per-entity later if a real requirement appears.

Durations in seconds; dayparts as local HH:mm

Integer seconds are unambiguous and easy to sum. Dayparts are wall-clock strings resolved in the office's timezone at manifest-computation time — timezone stays first-class.

Migrations

We use TypeORM migrations, not synchronize: true. Auto-sync is convenient but unsafe (it can silently drop columns); migrations are explicit, reviewable, and reproducible across dev / CI / production — the same discipline as code.

  • The first migration creates all tables for the entities above.
  • Workflow: change an entity → migration:generate → review the SQL → commit → migration:run. Generated SQL is always read before it's trusted.
  • A standalone data-source.ts configures the connection for the TypeORM CLI; the NestJS app configures the same connection via TypeOrmModule.

Testing stance for this slice

Per our standards we do test-driven development for logic — but entity definitions are declarative schema, not logic, so unit-testing them adds little (you'd be asserting that a decorator is present). Following KISS/YAGNI, the meaningful tests arrive with the next slices:

  • Repository/service logic (CRUD, the "exactly one target" invariant, schedule overlap resolution) — unit-tested, TDD-style, with the repository mocked.
  • Migration + mapping — verified by running the migration against a real Postgres (an integration check), since Postgres-specific types (enum, jsonb) don't map to an in-memory database faithfully.

So this slice is verified by compiling and by running the migration against Postgres; behavioural unit tests begin with the service layer.

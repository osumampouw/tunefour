The Server & NestJS

Reading apps/server with a Spring background. NestJS is built on the same three pillars as Spring — decorators (annotations) + dependency injection + modules — so most of it will map onto what you already know.

If you know Spring, you're 80% of the way there

NestJS ↔ Spring, at a glance

NestJS is directly inspired by Angular, but conceptually it lines up with Spring almost one-to-one:

NestJSSpring equivalentRole
@Module@Configuration / @SpringBootApplicationGroups controllers + providers
@Controller('health')@RestController @RequestMappingHTTP route-handler class
@Get(), @Post()@GetMapping, @PostMappingMap a method to an HTTP verb
@Injectable()@Service / @ComponentA DI-managed bean
constructor injectionconstructor injectionHow dependencies arrive
GuardsSpring Security filtersAuth / authorization
InterceptorsAOP / HandlerInterceptorCross-cutting logic around handlers
Pipesargument resolvers / validatorsValidate & transform input
Exception filters@ControllerAdvice / @ExceptionHandlerTurn errors into responses
The one big difference Spring does classpath component scanning — it finds your @Services automatically. Nest is explicit: you register controllers/providers in a @Module. Slightly more boilerplate, but the wiring is visible and easy to trace.

Walking the server code

src/main.ts — the bootstrap

Like Spring's main() + SpringApplication.run(...).

import 'reflect-metadata';                        // enables decorator/reflection machinery
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule); // build the DI container from the root module
  app.enableCors();                                // let the browser admin portal call the API
  const port = Number(process.env.PORT ?? 3001);
  await app.listen(port);                          // start the HTTP server
}
void bootstrap();                                  // `void` = intentionally not awaiting

NestFactory.create(AppModule) boots the whole app from the root module — it constructs the IoC container, instantiates providers, and wires everything, exactly like Spring's application context.

src/app.module.ts — the root module

Like a @Configuration class.

@Module({
  controllers: [HealthController],   // register controllers here
  // providers: [...], imports: [...], exports: [...]  ← services, other modules
})
export class AppModule {}

As the app grows, you split into feature modules (AuthModule, DevicesModule) and list them in imports — Spring's @Import / module organization.

src/health/health.controller.ts — a controller

@Controller('health')     // route prefix: /health   (≈ @RequestMapping)
export class HealthController {
  @Get()                  // handle GET /health       (≈ @GetMapping)
  check() {
    return { status: 'ok', /* ... */ };   // auto-serialized to JSON (≈ @ResponseBody)
  }
}

Return an object and Nest serializes it to JSON automatically, just like Spring's @RestController.

Why the decorators work at all TypeScript decorators (@Controller, @Get) emit metadata that Nest reads via reflection at startup — the same "annotations + reflection" model as Java/Spring. That's why tsconfig.base.json sets experimentalDecorators + emitDecoratorMetadata, and why main.ts imports reflect-metadata (the reflection polyfill). Without those, the decorators would be inert.

The request lifecycle

A request flows through the same kind of chain as Spring's filter/interceptor stack:

request
   ↓  Middleware        (≈ Servlet filters)
   ↓  Guards            (≈ Spring Security — allow/deny)
   ↓  Interceptors      (≈ AOP — wrap the handler, before)
   ↓  Pipes             (≈ validate/transform the input)
   ↓  Controller handler → Service (business logic)
   ↑  Interceptors      (after — shape the response)
response

We only use Controllers so far. Guards (auth), Pipes (validation), and Interceptors arrive in later phases.

Why multiple @nestjs/* dependencies?

Yes, this is standard — it's how Nest is designed. The framework is deliberately split into small, focused packages so you install only what you use and can swap pieces (e.g. the HTTP engine). Every Nest project looks like this; you're installing official sub-packages, not splitting arbitrarily.

Runtime dependencies

PackageWhat it is
@nestjs/coreThe engine — DI container, module system, framework runtime. Required.
@nestjs/commonThe everyday toolkit — the decorators (@Controller, @Get, @Injectable, @Module), pipes, guards, interfaces. Required; what you import from constantly.
@nestjs/platform-expressThe HTTP adapter. Nest is platform-agnostic — this binds it to Express. Swap for @nestjs/platform-fastify to run on Fastify instead.
reflect-metadataThe reflection polyfill the decorators rely on.
rxjsObservables, which Nest uses internally (e.g. in interceptors).

Dev-only dependencies

@nestjs/cliThe nest command (build, generate). A tool, not shipped to production.
@nestjs/schematicsThe generators the CLI uses. Dev-only.
The key design idea The core / common / platform split means the framework core is decoupled from the HTTP layer — Express vs Fastify is a one-package swap, and the runtime stays lean. Later phases add more on demand: @nestjs/websockets + @nestjs/platform-socket.io (real-time gateway), @nestjs/jwt + @nestjs/passport (auth), @nestjs/config (env config).

Follow-up questions

Q1. How does an empty export class AppModule {} carry all the controllers & routes?

The class only looks empty. The magic is the @Module(...) decorator: a decorator is just a function that runs when the class is defined and attaches metadata to it. The class body stays empty because the wiring info lives in that metadata, not in code you write inside the braces.

This code:

@Module({ controllers: [HealthController] })
export class AppModule {}

is essentially shorthand for:

class AppModule {}
// the decorator is a function call that runs at definition time:
Module({ controllers: [HealthController] })(AppModule);
// ...which internally does something like:
Reflect.defineMetadata('controllers', [HealthController], AppModule);

So the class becomes a token (an identity/key) that metadata hangs off of. The same thing happens to the controller:

@Controller('health')   // stores path 'health' as metadata on the class
class HealthController {
  @Get()                // stores {method: GET, path: ''} as metadata on `check`
  check() { /* ... */ }
}

Then at startup, NestFactory.create(AppModule) reads that metadata via reflection and wires everything:

1. read AppModule's metadata            → finds [HealthController]
2. read HealthController's @Controller   → prefix "/health"
3. read each method's @Get/@Post         → check() handles GET ""
4. register route with Express           → GET /health → HealthController.check()
Exactly like Spring @RestController class Foo {} is also an "empty" class — the annotations carry the information and Spring reads them by reflection at startup. Nest is the same idea; the decorator + reflect-metadata is the TypeScript equivalent of Java annotations + reflection.
Why a class and not a plain object? The class doubles as a DI token and can have a constructor for injected dependencies later (e.g. constructor(private svc: FooService) {}). Here it needs none, so the body is empty — but it's still the identity Nest keys the metadata to.

Q2. app.enableCors() — is the default "no CORS"? How does it work with the browser?

Yes — by default Nest sends no CORS headers, and enableCors() turns them on. But the key thing to understand: CORS is enforced by the browser, not the server.

What CORS is

Browsers enforce the Same-Origin Policy: JavaScript running on one origin may not read responses from a different origin unless that server explicitly opts in. An "origin" = scheme + host + port, so these are different origins:

http://localhost:3000   ← the admin portal (Next.js)
http://localhost:3001   ← the API (NestJS)  — different port = different origin

So the admin portal calling the API is a cross-origin request — which is exactly why we need CORS.

The flow

Browser JS at :3000 → fetch("http://localhost:3001/health")

WITHOUT enableCors():
   server responds, but with NO Access-Control-Allow-Origin header
   → browser BLOCKS the JS from reading the response (CORS error in console)

WITH app.enableCors():
   server adds  Access-Control-Allow-Origin: *   (default)
   → browser allows the JS to read the response ✅

Preflight: for "non-simple" requests (custom headers, methods like PUT/DELETE, or a JSON body), the browser first sends an automatic OPTIONS "preflight" asking "am I allowed?" The server must answer with Access-Control-Allow-Methods/Headers. Nest handles this for you once CORS is enabled.

Two things worth knowing
  • curl / server-to-server calls ignore CORS entirely — there's no browser to enforce it. CORS only ever affects browser JavaScript.
  • enableCors() with no args allows all origins (*) — fine for local dev, but in production you'd lock it down: app.enableCors({ origin: 'https://admin.tunefour.com', credentials: true }).

Q3. In production, do you need Nest at runtime? Does the CLI compile everything to plain JS?

Both parts of your understanding are correct — let me split it into build-time vs runtime.

PhaseWhat runsNeeds which packages
Build (dev/CI) nest build compiles TypeScript → plain JavaScript into dist/. Decorators become ordinary JS function calls. The CLI (@nestjs/cli, @nestjs/schematics) — dev-only.
Runtime (production) node dist/main.js — plain Node runs the compiled JS. Nest's engine reads the metadata, builds the DI container, and registers Express routes. The runtime libs: @nestjs/core, @nestjs/common, @nestjs/platform-express, reflect-metadata, rxjs.

So the sequence is:

TypeScript (with decorators)
      │  nest build   (CLI, dev-time — uses tsc under the hood)
      ▼
plain JavaScript in dist/   ← decorators are now vanilla JS calls like Module(...)(AppModule)
      │  node dist/main.js   (production)
      ▼
Nest runtime engine reads the metadata (via reflect-metadata) and wires up Express

Key points:

  • The CLI is NOT needed in production — it's a build tool. A production install (pnpm install --prod) skips devDependencies, so no CLI ships.
  • The runtime @nestjs/* packages ARE needed in production — the compiled dist/ code require()s them, and the framework does its DI/reflection/routing work at runtime.
  • The "decoration" (attaching metadata) happens the moment the JS module loads (the decorator function calls execute); Nest's engine then reads that metadata at bootstrap. It's all plain JavaScript by then — the TypeScript is long gone.

Q4. If a file exports two classes, how does Nest know which one to decorate?

Common misconception: export has nothing to do with which class gets decorated. A decorator binds to whatever class declaration it sits directly above — it's pure adjacency, decided by the language, not by Nest. So with two classes, each has its own decorator and there's zero ambiguity:

@Module({ controllers: [HealthController] })
export class AppModule {}          // ← this @Module decorates AppModule

@Module({ providers: [FooService] })
export class SomethingModule {}    // ← this @Module decorates SomethingModule

Recall the desugaring — each decorator is a function call receiving that specific class, so nothing is guessed:

class AppModule {}
Module({ controllers: [HealthController] })(AppModule);   // bound to AppModule

class SomethingModule {}
Module({ providers: [FooService] })(SomethingModule);     // bound to SomethingModule

export just, separately, makes the class importable from other files.

So how does Nest know which module is the root?

Not from export, and not by scanning your files — you tell it explicitly in main.ts:

const app = await NestFactory.create(AppModule);   // ← AppModule is the root, by name

From there Nest discovers everything else by following the root's imports list. So SomethingModule only becomes part of the app if AppModule (or a module it imports) references it:

@Module({
  imports: [SomethingModule],        // ← this is how SomethingModule gets wired in
  controllers: [HealthController],
})
export class AppModule {}
Two independent things
  • Which class a decorator decorates → the class directly below it (language rule, unambiguous).
  • Which module is the app root → whichever you pass to NestFactory.create(...) — explicit, not inferred.
A class you export but never pass as root and never import into the graph is simply unused — Nest never touches it.

Q5. Why call bootstrap() with void — and if you use .catch(), do you still need it?

bootstrap is async, so calling it returns a Promise. The void operator evaluates the expression and discards the result — so void bootstrap() starts the server but throws away the returned Promise.

The "floating promise" problem

Calling an async function without await or .then/.catch leaves a floating promise — one nobody is watching, usually a sign of a forgotten await. We can't await here because this is the top level of a CommonJS module (no top-level await). So the call must be un-awaited — and we mark that intent:

bootstrap();        // ⚠️ floating — is the missing await a bug?
void bootstrap();   // ✅ explicit: intentionally not awaiting (fire-and-forget)
Caveat: void ignores errors void silences the "floating" concern but does not handle a rejection. If startup fails, that's an unhandled rejection. So the more robust pattern for a startup function is to catch and exit: 
bootstrap().catch((err) => {
  console.error('Failed to start tunefour-server', err);
  process.exit(1);
});
This is what main.ts uses.

With .catch(), do you also need void? No.

Attaching a .catch() handler handles the promise's rejection, which is exactly what makes it "not floating." void and .catch() are two different ways to satisfy the same rule:

FormMeaning
void promise"I'm ignoring this promise entirely" (including any error).
promise.catch(fn)"I'm handling this promise's rejection." — the stronger choice.

Since .catch() already makes the promise non-floating, void bootstrap().catch(...) would be redundant. Just bootstrap().catch(...) is correct and complete.

Config note The rule behind all this is @typescript-eslint/no-floating-promises, a type-checked rule. Our current ESLint config uses the plain recommended set (not type-checked), so it isn't enforced yet — the void/.catch() habit is about intent and correctness, and will matter if we enable type-checked lint later.

Tunefour — Tech Stack Guide

A friendly tour of every technology in this project, written for an experienced developer who is new to this particular stack.

You already know: Node.js, npm, nvm, ESLint. This guide bridges from there to everything else — TypeScript, pnpm, Turborepo, React, Next.js, NestJS, Electron, Docker, Terraform — and shows how each maps to the files in this repo.

The big picture

Tunefour is a monorepo: several related applications and shared libraries living in one Git repository, managed together. Here is how the pieces relate.

              ┌─────────────────────────── CLOUD ───────────────────────────┐
  Admin      │   Next.js admin portal ──┐                                  │
  (browser)  │                              ▼                                  │
             │                     NestJS API + WebSocket  ── Postgres / Redis │
             │                              │                     / Object store │
             └──────────────────────────────┼──────────────────────────────────┘
                                            │  (internet)
             ┌──────────────────────────────┼──────────────────────────────────┐
             │  Office mini-PC + TV          ▼                                   │
             │   Electron kiosk app  ◄── pulls schedule, caches, plays offline│
             └───────────────────────────────────────────────────────────────── ┘

  Shared across all of the above:  TypeScript language · pnpm installs ·
  Turborepo orchestrates builds · packages/shared-types holds common types
  Local dev services (Docker): Postgres + Redis + MinIO   ·   Cloud infra (Terraform)

Think in three groups, which is how the rest of this guide is organised:

  • Language & tooling — the things every part of the codebase uses: TypeScript, pnpm, Turborepo, ESLint/Prettier, Zod.
  • Applications — the actual programs: a server (NestJS), web portals (Next.js, built on React), and the TV client (Electron).
  • Data & infrastructure — where state lives and how we run/host it: Postgres, Redis, object storage, Docker, Terraform.

TypeScript language

TypeScript is JavaScript with a type system. You write almost the same code, but you also describe the shapes of your data — and a compiler checks that you use them consistently before the code ever runs. It compiles down to plain JavaScript that Node/browsers execute.

Coming from JavaScript Everything you know still works. You're adding annotations like : string, : number, and defining interfaces / types. The payoff: your editor autocompletes everything, and typos like user.emial become errors at build time instead of 2am bugs. 
// JavaScript you know:
function greet(user) { return "Hi " + user.name; }

// TypeScript: describe the shape, get checking + autocomplete
interface User { name: string; email: string; }
function greet(user: User): string {
  return "Hi " + user.name;      // user.namee → compile error
}
Why in Tunefour The server, the web portals, and the TV client all share the same data shapes (e.g. the DeviceManifest a server sends to a client). We define those once in packages/shared-types and every app imports them — so if the server changes a field, the client won't compile until it's updated. That safety across a distributed system is the whole reason we use TypeScript.

pnpm package manager

pnpm does the same job as npm — installs dependencies, runs scripts — but faster and more disk-efficient, and it's excellent at monorepos.

Coming from npm The commands rhyme: npm install → pnpm install, npm run build → pnpm build, npm install left-pad → pnpm add left-pad. Two differences that matter:
  1. One global store. Each package version is downloaded once to a shared store and hard-linked into projects — not re-copied every time. Big disk + speed win.
  2. Stricter. Your code can only import packages you actually declared in package.json (npm lets you accidentally use a dependency's dependency). Fewer "works on my machine" surprises.
Why in Tunefour Workspaces. Our pnpm-workspace.yaml declares apps/* and packages/* as one linked workspace. That lets apps/server depend on "@tunefour/shared-types": "workspace:*" and pnpm links it to our local source — no publishing to a registry. This is the glue that makes the monorepo work.
You saw this already Remember the allowBuilds prompt during install? That's pnpm's supply-chain safety: it won't run a dependency's install scripts (like Electron downloading a binary) unless you approve it.

Turborepo build orchestrator

Turborepo (the turbo command) doesn't compile or bundle anything itself. It's a coordinator: it decides what to run, in what order, in parallel, and — crucially — what to skip because nothing changed.

Coming from npm scripts With plain npm in a monorepo you'd write shell scripts to build package A before app B, and everything rebuilds every time. Turbo reads a dependency graph and does this for you, then caches results so a second build is near-instant.

The three ideas

IdeaWhat it means here
Task graph"build": { "dependsOn": ["^build"] } in turbo.json — the ^ means "build my dependencies first," so shared-types always builds before the apps that use it.
ParallelismApps that don't depend on each other build at the same time. That's why our full build finished in ~8 seconds.
CachingTurbo hashes every input; if unchanged, it replays the cached output instead of rebuilding. You literally saw cache hit, replaying logs on the second build.
Why in Tunefour With 5+ packages (and growing), running pnpm build / lint / typecheck once at the root does the right thing everywhere, fast — no hand-wired ordering.

ESLint & Prettier code quality

You know ESLint already. The one distinction worth nailing down is how it differs from Prettier — they're often confused because both "clean up your code."

ESLint — correctness

Catches bugs and risky patterns: unused variables, unsafe types, bad practices. Our shared rules live in packages/config and every package imports them via its eslint.config.mjs.

Prettier — formatting

Only reformats how code looks (quotes, indentation, line breaks) — never logic. Config is .prettierrc.json. It ends all style debates and keeps diffs clean.

They cooperate eslint-config-prettier (in our shared config) turns off ESLint's own style rules so the two never fight over formatting.
ESLint docs Prettier docs Why both (formatters vs linters)

Zod runtime validation

TypeScript types vanish at runtime (they're erased when compiled to JavaScript). So when data arrives from the network, TypeScript can't check it — it just trusts it. Zod fills that gap: you define a schema once, and get both a runtime validator and a TypeScript type from it.

import { z } from 'zod';

const DeviceManifestSchema = z.object({
  version: z.string(),
  checksum: z.string().regex(/^[a-f0-9]{64}$/), // must be a SHA-256 hex
});
type DeviceManifest = z.infer<typeof DeviceManifestSchema>; // the TS type, for free

// At runtime, verify untrusted input actually matches:
const manifest = DeviceManifestSchema.parse(dataFromServer); // throws if malformed
Why in Tunefour The TV client must never render a corrupt/malformed manifest (that's the fail-safe rule). It uses the Zod schema in packages/shared-types/src/manifest.ts to validate every manifest before acting on it.

React UI library

React is a library for building user interfaces out of components — reusable functions that return markup. Instead of manually poking the DOM (document.getElementById(...).innerHTML = ...), you describe what the UI should look like for a given state, and React updates the screen when the state changes.

Coming from vanilla JS / jQuery The mental shift: you stop writing "find this element and change it" (imperative) and start writing "given this data, here's the UI" (declarative). React figures out the minimal DOM changes. Components are just functions; the HTML-in-JS syntax is called JSX. 
function Welcome({ name }) {          // a component = a function
  return <h1>Hello, {name}</h1>;       // JSX: markup inside JS
}

function Counter() {
  const [count, setCount] = React.useState(0);  // state
  return <button onClick={() => setCount(count + 1)}>Clicked {count}</button>;
}
Why in Tunefour Our admin portal and front-desk view are UIs with lots of interactive state (forms, device lists, live status). React is the industry standard for that, and Next.js (next section) is built on top of it.
Official interactive tutorial Thinking in React Hooks: useState

Next.js web framework (admin, front-desk)

React by itself only handles the UI in the browser. A real web app also needs routing (which page for which URL), server-side rendering, a build system, and often some backend endpoints. Next.js is a full framework around React that provides all of that.

Coming from Node + a templating engine If you've built a site with Express + EJS/Handlebars, Next.js is the modern equivalent: it renders React on the server for a fast first paint, then "hydrates" it into an interactive app in the browser — best of both worlds. Routing is file-based: a file at app/page.tsx is the home page, app/devices/page.tsx is /devices. No route table to wire up. 
// apps/admin/app/page.tsx  →  serves the "/" route
export default function HomePage() {
  return <main><h1>Tunefour Admin</h1></main>;
}
Why in Tunefour Two of our apps are web portals (apps/admin, apps/frontdesk). Next.js gives us routing, a production build, and a clean place to talk to the NestJS API — without assembling a dozen libraries ourselves. You already ran it: next build produced the admin portal earlier.

NestJS backend framework (server)

NestJS is a framework for building the server — the API the portals and TV clients talk to. It runs on Node and, under the hood, uses Express (which you may know). Nest adds structure: a consistent way to organise code into modules, controllers, and services, with built-in support for validation, auth guards, and WebSockets.

Coming from Express In bare Express you wire routes and middleware however you like — flexible, but every project reinvents its structure. Nest is the "batteries-included, opinionated" layer: think Express with a rulebook (and if you've seen Java's Spring or Angular, the module/decorator style will feel familiar).
Nest conceptPlain-English job
ControllerHandles incoming HTTP requests for a route (e.g. GET /health). We built health.controller.ts.
ServiceHolds business logic, kept separate from HTTP handling so it's testable.
ModuleGroups related controllers/services (e.g. an AuthModule). app.module.ts is the root.
DecoratorThe @Get(), @Controller() annotations — metadata that tells Nest how to wire things.
@Controller('health')          // routes under /health
export class HealthController {
  @Get()                       // handles GET /health
  check() { return { status: 'ok' }; }
}
Why in Tunefour The server is the brain: auth, RBAC, the device manifest, scheduling, and the real-time WebSocket channel. Nest's structure keeps that many-moving-parts system organised and its guard/DI system is a natural fit for the pluggable auth we planned.

Electron desktop client (TV kiosk)

Electron lets you build a desktop application using web technologies (HTML/CSS/JS). It bundles a Chromium browser and Node.js together, so your app is a web page that also has full access to the operating system (files, auto-start, hardware).

Coming from web dev You already know how to build a web page. Electron wraps that page into a native .exe/app window. Apps you use daily — VS Code, Slack, Discord — are Electron apps. It has two "sides": the main process (Node.js — controls windows, OS access) and the renderer (the Chromium page — your UI). 
// apps/client/src/main.ts — the main process
import { app, BrowserWindow } from 'electron';
app.whenReady().then(() => {
  const win = new BrowserWindow({ fullscreen: true, kiosk: true });
  win.loadFile('static/index.html');   // the page shown on the TV
});
Why in Tunefour The TV client must render rich content (images, video, HTML dashboards) full-screen, cache files locally, survive reboots, and auto-launch — a web page alone can't touch the filesystem or control the window like that. Electron gives us a browser for rendering plus Node for the offline cache, watchdog, and OS integration.
Reminder from setup We set allowBuilds: electron: false, so its ~100 MB runtime binary isn't downloaded yet. On a real dev machine you flip that to true (or run pnpm approve-builds) and pnpm --filter @tunefour/client dev opens the window.

Postgres · Redis · Object storage data

PostgreSQL

A rock-solid relational (SQL) database. It's our source of truth: offices, devices, playlists, schedules, users. If you've used any SQL database, you're home.

PostgreSQL tutorial

Redis

An in-memory key–value store — extremely fast. We use it for caching and to fan-out real-time messages across multiple server instances (the WebSocket relay we discussed).

Redis quick start

Object storage + CDN

Media files (video, images) don't belong in a database. They go in object storage (S3 / Google Cloud Storage), served fast worldwide via a CDN. Locally we fake S3 with MinIO.

MinIO docs

How they fit

Postgres = the facts. Redis = fast scratch space + message bus. Object storage = the big files. Each tool for what it's best at.

Docker local services & packaging

Docker packages software into containers — self-contained, isolated units that run identically on any machine. Instead of installing Postgres, Redis, and MinIO by hand (different on every laptop), you describe them once and Docker runs them.

Coming from "install it on my machine" A container is like a lightweight, disposable mini-computer with exactly one program and its dependencies inside. "Works on my machine" disappears because the container is the machine. An image is the blueprint; a container is a running instance of it.

Docker Compose runs several containers together from one file. Our docker-compose.yml defines Postgres + Redis + MinIO, so local dev is a single command:

docker compose up -d      # start Postgres, Redis, MinIO in the background
docker compose ps         # see what's running
docker compose down       # stop them
Why in Tunefour Everyone on the team gets identical local databases with zero manual setup, and the same images run in the cloud. (Later phases also package the NestJS server itself as a container for deployment.)

Terraform infrastructure as code

Terraform lets you define your cloud infrastructure in text files — servers, databases, networks, storage buckets — and create/update it with a command, instead of clicking around a cloud console. This is called "Infrastructure as Code."

The mental model You declare the end state you want ("one Postgres database, one storage bucket, a load balancer"), and Terraform figures out the API calls to make reality match. It's version-controlled, reviewable, and repeatable — the same discipline as code, applied to servers. 
# example.tf — declare what you want to exist
resource "aws_s3_bucket" "media" {
  bucket = "tunefour-media"
}
terraform plan     # preview what would change
terraform apply    # make it so
Why in Tunefour With real infrastructure across a cloud provider, doing it by hand is error-prone and impossible to reproduce. Terraform keeps our cloud setup in infra/, reviewable in Git like everything else. This is post-MVP — safe to learn last.

Folder structure

Here's the repo, annotated. The two top-level ideas: apps/ holds runnable programs, packages/ holds shared libraries they import.

tunefour/ ├─ apps/ # runnable programs │ ├─ server/ # NestJS API + WebSocket gateway (the backend) │ ├─ admin/ # Next.js admin portal (web UI) │ ├─ frontdesk/ # Next.js front-desk view (welcome-message sender) │ └─ client/ # Electron kiosk app for the TVs ├─ packages/ # shared libraries (not run directly) │ ├─ shared-types/ # TS types + Zod manifest schema, imported by every app │ ├─ auth/ # pluggable AuthProvider (Local now, Keycloak later) │ └─ config/ # shared ESLint config ├─ infra/ # Terraform + Dockerfiles for deployment ├─ docs/ # this guide, plus API/design docs ├─ docker-compose.yml # local Postgres + Redis + MinIO ├─ turbo.json # Turborepo task pipeline ├─ pnpm-workspace.yaml # tells pnpm where the packages are ├─ tsconfig.base.json # shared TypeScript settings all packages extend ├─ .nvmrc # pins Node version (24) for nvm — familiar! └─ IMPLEMENTATION_PLAN.md # the full build plan & phases

Why a monorepo?

All these apps share types and evolve together. Keeping them in one repo means a single pnpm install, atomic changes across apps (update a type and all consumers in one commit), and one place for CI. Turborepo makes building them fast; pnpm workspaces makes them link to each other locally.

Anatomy of one package

Every app/package follows the same pattern you already recognise from Node:

apps/server/ ├─ package.json # its dependencies + scripts (dev, build, lint...) ├─ tsconfig.json # extends the root tsconfig.base.json ├─ eslint.config.mjs # imports the shared config └─ src/ # the actual TypeScript source ├─ main.ts # entry point (starts the server) ├─ app.module.ts # root NestJS module └─ health/ # a feature folder └─ health.controller.ts

How it all runs together

A day-in-the-life of the commands, all run from the repo root:

CommandWhat happens
nvm useSwitches to Node 24 (reads .nvmrc). Same nvm you know.
pnpm installInstalls dependencies for all apps/packages at once and links the workspace packages together.
docker compose up -dStarts Postgres, Redis, MinIO locally in containers.
pnpm devTurbo runs every app's dev script in parallel — server, admin, etc. — with hot reload.
pnpm buildTurbo builds everything in dependency order, using the cache to skip unchanged work.
pnpm lint / pnpm typecheckRuns ESLint / the TypeScript compiler across all packages.
pnpm --filter @tunefour/server devRuns a script in just one package (the --filter flag).
The flow of a request (end to end) An admin opens the Next.js portal in their browser → it calls the NestJS API → Nest reads/writes Postgres and computes each device's manifest → it pushes an update over WebSocket (fanned out via Redis) → the Electron client on the TV downloads new media from object storage, validates it with the Zod schema from shared-types, and plays it. Every hop shares the same TypeScript types.
